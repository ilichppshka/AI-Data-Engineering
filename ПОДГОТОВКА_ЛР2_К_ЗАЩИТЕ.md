# Лабораторная работа 2: форматы хранения и SQL

Этот конспект нужен для понимания ЛР2 и подготовки к вопросам преподавателя.
В работе данные переводятся из исходных CSV-файлов в колоночный формат Parquet,
загружаются в аналитическое хранилище DuckDB, а затем обрабатываются SQL-запросами.

В ЛР2 есть две главные идеи:

1. **Одна строка итоговой таблицы должна иметь понятный смысл.** В
   `orders_enriched` одна строка означает один заказ.
2. **Таблицы с отношением один-ко-многим нужно сначала свернуть до нужного
   уровня, а потом соединять.** Иначе строки и суммы размножаются.

Итоговая схема работы выглядит так:

```text
исходные CSV
    ↓
Parquet-файлы
    ↓
таблицы raw_* в DuckDB
    ↓
orders_enriched: одна строка на заказ
    ↓
monthly_revenue: одна строка на месяц
    ↓
Parquet-витрина для передачи другим системам
```

## Что является результатом работы

В хранилище создаются две таблицы.

### `orders_enriched`

Одна строка соответствует одному заказу.

| Колонка | Смысл |
|---|---|
| `order_id` | Идентификатор заказа |
| `customer_id` | Идентификатор покупателя |
| `order_status` | Статус заказа |
| `order_date` | Дата покупки, тип `DATE` |
| `payment_total` | Сумма всех платёжных операций заказа |
| `payment_count` | Количество платёжных операций заказа |
| `n_items` | Количество товарных позиций заказа |
| `items_total` | Сумма цен товаров в заказе |
| `freight_total` | Сумма доставки в заказе |

Таблица должна:

- содержать столько строк, сколько `raw_orders`;
- иметь уникальный `order_id`;
- сохранять заказы без платежей и без позиций;
- содержать нули вместо пропусков в числовых показателях;
- давать те же общие суммы платежей и товаров, что и исходные таблицы.

### `monthly_revenue`

Одна строка соответствует одному календарному месяцу.

| Колонка | Смысл |
|---|---|
| `month` | Первый день месяца, тип `DATE` |
| `n_orders` | Количество заказов за месяц |
| `revenue` | Выручка за месяц, сумма `items_total` |
| `revenue_cumulative` | Накопительная выручка с начала истории |
| `revenue_prev` | Выручка предыдущего месяца |

Для первого месяца `revenue_prev` равен `NULL`, потому что предыдущего месяца
в наборе нет.

## Термины и определения

| Термин | Определение |
|---|---|
| **Raw layer** | Слой исходных данных. В нём файлы хранятся в том виде, в котором пришли из источника. |
| **Схема данных** | Набор колонок, их типов и структуры таблицы. |
| **CSV** | Текстовый табличный формат, где строки и значения разделены специальными символами. |
| **Parquet** | Колоночный бинарный формат, который хранит данные и их схему. |
| **Строковое хранение** | Значения одной строки лежат рядом. Удобно для чтения и изменения отдельных записей. |
| **Колоночное хранение** | Значения одной колонки лежат рядом. Удобно для аналитики, когда нужны несколько колонок из большого набора. |
| **DuckDB** | Встраиваемая аналитическая СУБД. Она работает внутри процесса Python и не требует отдельного сервера. |
| **Хранилище данных** | Место, где данные собраны в удобные для аналитики таблицы и схемы. |
| **OLTP** | Обработка оперативных операций: быстро найти или изменить отдельную запись. |
| **OLAP** | Аналитическая обработка: прочитать много строк и посчитать агрегаты. |
| **Grain, или зерно таблицы** | Смысл одной строки. У `orders_enriched` зерно — один заказ, у `monthly_revenue` — один месяц. |
| **Ключ соединения** | Колонка, по которой сопоставляются строки таблиц. Здесь обычно это `order_id`. |
| **1:1** | Одной строке первой таблицы соответствует одна строка второй. Заказ и покупатель в этих данных имеют такую связь. |
| **1:N** | Одной строке первой таблицы соответствует много строк второй. Заказ и платежи, заказ и позиции — такие связи. |
| **JOIN** | Операция соединения таблиц по общему ключу. |
| **LEFT JOIN** | Соединение, которое сохраняет все строки левой таблицы, даже если справа соответствия нет. |
| **Fan-out, или размножение строк** | Ситуация, когда одна строка после соединения превращается в несколько строк из-за связи 1:N. |
| **Агрегация** | Сведение нескольких строк к одному результату с помощью `SUM`, `COUNT`, `AVG` и других функций. |
| **CTE** | Именованный промежуточный запрос внутри `WITH ... AS (...)`. |
| **NULL** | Отсутствующее или неизвестное значение. Это не то же самое, что число 0. |
| **COALESCE** | Функция, которая возвращает первое значение, не равное `NULL`. |
| **Оконная функция** | Расчёт по группе соседних или связанных строк, который не схлопывает строки в одну. |
| **LAG** | Оконная функция для получения значения из предыдущей строки. |
| **Накопительный итог** | Сумма от первой строки до текущей строки по заданному порядку. |
| **Витрина** | Подготовленная таблица для отчёта, аналитика или другого потребителя данных. |
| **Идемпотентность** | Повторный запуск даёт тот же результат, а не добавляет дубликаты. |

## Почему прямое соединение даёт неправильные суммы

У заказа могут быть несколько позиций и несколько платежей. Допустим, у одного
заказа три позиции и два платежа:

```text
3 позиции × 2 платежа = 6 строк после прямого JOIN
```

Каждый платёж окажется повторён три раза, а каждая позиция — два раза. Поэтому
сумма платежей и сумма товаров станут завышенными.

Правильная последовательность:

```text
raw_payments → сгруппировать по order_id → одна строка на заказ
raw_items    → сгруппировать по order_id → одна строка на заказ
raw_orders   → LEFT JOIN с двумя свёртками
```

После такой подготовки каждая присоединяемая таблица имеет тот же grain, что и
левая таблица заказов.

## Задание 1: `orders_enriched`

### Общий смысл запроса

Запрос строит таблицу на уровне заказа. Сначала два CTE отдельно считают
платежи и товарные позиции, затем эти результаты соединяются с `raw_orders`.

```sql
CREATE OR REPLACE TABLE orders_enriched AS
WITH pay AS (
    SELECT
        order_id,
        SUM(payment_value) AS payment_total,
        COUNT(*) AS payment_count
    FROM raw_payments
    GROUP BY order_id
),
items AS (
    SELECT
        order_id,
        COUNT(*) AS n_items,
        SUM(price) AS items_total,
        SUM(freight_value) AS freight_total
    FROM raw_items
    GROUP BY order_id
)
SELECT
    o.order_id,
    o.customer_id,
    o.order_status,
    CAST(o.order_purchase_timestamp AS DATE) AS order_date,
    COALESCE(p.payment_total, 0) AS payment_total,
    COALESCE(p.payment_count, 0) AS payment_count,
    COALESCE(i.n_items, 0) AS n_items,
    COALESCE(i.items_total, 0) AS items_total,
    COALESCE(i.freight_total, 0) AS freight_total
FROM raw_orders AS o
LEFT JOIN pay AS p USING (order_id)
LEFT JOIN items AS i USING (order_id)
```

### Разбор команд задания 1

#### `CREATE OR REPLACE TABLE`

```sql
CREATE OR REPLACE TABLE orders_enriched AS
SELECT ...
```

Создаёт таблицу из результата запроса. Если таблица уже существует, она
заменяется новой версией. Это делает ячейку идемпотентной: повторный запуск не
добавляет второй набор строк к старому результату.

#### `WITH pay AS (...)` и `WITH items AS (...)`

Это два CTE — именованных промежуточных запроса.

`pay` собирает платежи на уровне заказа:

```sql
SELECT
    order_id,
    SUM(payment_value) AS payment_total,
    COUNT(*) AS payment_count
FROM raw_payments
GROUP BY order_id
```

- `SUM(payment_value)` считает общую сумму платежей заказа;
- `COUNT(*)` считает количество платёжных строк;
- `GROUP BY order_id` оставляет одну строку на заказ.

`items` делает то же для товарных позиций:

```sql
SELECT
    order_id,
    COUNT(*) AS n_items,
    SUM(price) AS items_total,
    SUM(freight_value) AS freight_total
FROM raw_items
GROUP BY order_id
```

- `COUNT(*)` считает позиции заказа;
- `SUM(price)` считает стоимость товаров;
- `SUM(freight_value)` считает доставку;
- `GROUP BY order_id` предотвращает размножение строк при последующем JOIN.

#### `SELECT`

`SELECT` задаёт колонки, которые попадут в итоговую таблицу. Префиксы `o`, `p`
и `i` обозначают таблицы или CTE, которым эти колонки принадлежат.

#### `CAST(... AS DATE)`

```sql
CAST(o.order_purchase_timestamp AS DATE) AS order_date
```

Превращает строковое или временное значение даты покупки в тип `DATE`. Время
отбрасывается, потому что для задания нужна календарная дата.

#### `LEFT JOIN ... USING (order_id)`

```sql
FROM raw_orders AS o
LEFT JOIN pay AS p USING (order_id)
LEFT JOIN items AS i USING (order_id)
```

`LEFT JOIN` сохраняет все заказы из `raw_orders`. Если у заказа нет платежей
или позиций, соответствующих строки в `pay` или `items` не будет, но сам заказ
останется.

`USING (order_id)` — сокращённая запись соединения по одноимённой колонке:

```sql
ON o.order_id = p.order_id
```

#### `COALESCE`

```sql
COALESCE(p.payment_total, 0)
```

После `LEFT JOIN` для отсутствующего платежа получается `NULL`. `COALESCE`
заменяет его нулём. Это важно для числовых показателей: отсутствие платежа
означает нулевую сумму, а не неизвестную сумму.

### Что проверяется в задании 1

Проверка сравнивает:

- количество строк `orders_enriched` с количеством строк `raw_orders`;
- количество строк с количеством уникальных `order_id`;
- сумму `payment_total` с суммой `payment_value` в `raw_payments`;
- сумму `items_total` с суммой `price` в `raw_items`;
- сумму `freight_total` с суммой `freight_value` в `raw_items`;
- сумму `payment_count` с количеством платёжных строк;
- сумму `n_items` с количеством товарных строк;
- наличие `NULL` в ключевых и числовых колонках;
- тип `order_date` — он должен быть `DATE`.

Если сумма в `orders_enriched` больше суммы в источнике, обычно это означает
fan-out: платежи или позиции были присоединены до агрегации.

## Задание 2: `monthly_revenue`

### Общий смысл запроса

Вторая таблица строится из `orders_enriched`, потому что там уже одна строка на
заказ и показатель `items_total` не размножен.

```sql
CREATE OR REPLACE TABLE monthly_revenue AS
WITH monthly AS (
    SELECT
        CAST(date_trunc('month', order_date) AS DATE) AS month,
        COUNT(*) AS n_orders,
        SUM(items_total) AS revenue
    FROM orders_enriched
    GROUP BY 1
)
SELECT
    month,
    n_orders,
    revenue,
    SUM(revenue) OVER (
        ORDER BY month
        ROWS UNBOUNDED PRECEDING
    ) AS revenue_cumulative,
    LAG(revenue) OVER (
        ORDER BY month
    ) AS revenue_prev
FROM monthly
ORDER BY month
```

### Разбор команд задания 2

#### `date_trunc('month', order_date)`

Округляет дату до начала месяца. Например:

```text
2017-05-23 → 2017-05-01
```

Все заказы одного месяца получают одинаковое значение `month` и могут быть
собраны одной группой.

#### `GROUP BY 1`

`1` означает первую колонку в `SELECT`, то есть выражение с месяцем:

```sql
GROUP BY 1
```

Эквивалентная более подробная запись:

```sql
GROUP BY CAST(date_trunc('month', order_date) AS DATE)
```

В результате CTE `monthly` содержит одну строку на месяц.

#### `COUNT(*)` и `SUM(items_total)`

Поскольку `orders_enriched` имеет одну строку на заказ:

- `COUNT(*)` правильно считает заказы;
- `SUM(items_total)` правильно считает выручку.

Если считать `COUNT(*)` напрямую в `raw_items`, получится количество товарных
позиций, а не количество заказов.

#### Оконная функция `SUM(...) OVER (...)`

```sql
SUM(revenue) OVER (
    ORDER BY month
    ROWS UNBOUNDED PRECEDING
)
```

Она считает накопительную сумму. Для каждой строки берётся диапазон от первой
строки до текущей:

```text
январь                 январская выручка
февраль                январь + февраль
март                   январь + февраль + март
```

`GROUP BY` уменьшает количество строк, а оконная функция оставляет одну строку
на месяц и добавляет к ней дополнительный расчёт.

#### Оконная функция `LAG`

```sql
LAG(revenue) OVER (ORDER BY month) AS revenue_prev
```

Берёт значение `revenue` из предыдущей строки в порядке месяцев. Для первой
строки предыдущего значения нет, поэтому получается `NULL`.

#### `ORDER BY month`

Задаёт хронологический порядок. Он нужен и для вывода месяцев, и для правильной
работы `SUM ... OVER` и `LAG`.

#### `ROWS UNBOUNDED PRECEDING`

Явно задаёт окно от начала набора до текущей строки. Это делает смысл
накопительного итога очевидным и не даёт случайно посчитать другой диапазон.

### Что проверяется в задании 2

Проверка убеждается, что:

- в таблице одна строка на уникальный месяц;
- количество месяцев совпадает с `orders_enriched`;
- сумма `n_orders` равна количеству заказов;
- сумма `revenue` равна сумме `items_total`;
- `revenue_cumulative` правильно рассчитан в каждой строке;
- последнее значение `revenue_cumulative` равно всей выручке;
- `revenue_prev` совпадает с выручкой предыдущего месяца;
- в тексте SQL действительно используются оконные функции `OVER (...)`.

## Команды Python, которые окружают SQL

### `con.execute(sql_task1)` и `con.execute(sql_task2)`

`con` — соединение с DuckDB. Метод `execute` отправляет SQL-строку в базу и
выполняет её.

```python
con.execute(sql_task1)
con.execute(sql_task2)
```

В этих двух случаях команда создаёт или пересоздаёт таблицу.

### `con.execute("SELECT ...").df()`

```python
con.execute("SELECT * FROM orders_enriched LIMIT 5").df()
```

Выполняет запрос и переводит результат в `pandas.DataFrame`, чтобы его было
удобно посмотреть в ноутбуке. `LIMIT 5` ограничивает вывод первыми пятью
строками и не меняет саму таблицу.

### Проверки

```python
check_task_1(con)
check_task_2(con, sql_task2)
lab02_result()
```

- `check_task_1(con)` проверяет структуру и значения `orders_enriched`;
- `check_task_2(con, sql_task2)` проверяет `monthly_revenue` и текст SQL;
- `lab02_result()` собирает общий результат ЛР2 и проверяет артефакты.

## Выгрузка результата в Parquet

После создания таблиц выполняется:

```python
con.execute(f"""
    COPY orders_enriched TO '{(paths.STAGING / "lab02_orders_enriched.parquet").as_posix()}'
    (FORMAT PARQUET)
""")
```

`COPY ... TO` записывает результат таблицы во внешний файл. Параметр
`FORMAT PARQUET` указывает колоночный формат. Это нужно, чтобы передать
`orders_enriched` процессу или команде, у которых нет прямого доступа к DuckDB.

## Важные различия, которые нужно уметь объяснить

### `NULL` и `0`

`NULL` означает отсутствие значения или неизвестность. `0` означает, что
значение известно и равно нулю. Для заказа без платежей в итоговой таблице
нужен `payment_total = 0`, поэтому используется `COALESCE`.

### `COUNT(*)` и `COUNT(DISTINCT order_id)`

`COUNT(*)` считает строки результата. Если строки размножились после JOIN, он
будет завышен. `COUNT(DISTINCT order_id)` считает уникальные заказы и помогает
обнаружить fan-out. В `orders_enriched`, где одна строка действительно равна
одному заказу, эти два количества должны совпадать.

### `GROUP BY` и оконная функция

`GROUP BY` превращает много исходных строк в одну строку группы. Оконная функция
считает по соседним или связанным строкам, но сохраняет исходное количество
строк. Поэтому месячная агрегация сделана через `GROUP BY`, а накопительный итог
и предыдущее значение — через `OVER`.

### `LEFT JOIN` и `INNER JOIN`

`INNER JOIN` оставляет только строки, для которых есть пара справа. `LEFT JOIN`
сохраняет всю левую таблицу. Для `orders_enriched` нужен `LEFT JOIN`, потому что
заказ без платежа или позиции всё равно должен остаться в результате.

## Архитектурный вопрос про библиотеку

В конце ноутбука описана система из сорока филиалов. Каждый филиал раз в ночь
передаёт CSV с выдачами и возвратами. Нужно одновременно строить месячные
отчёты, отвечать библиотекарю о текущих книгах читателя и хранить историю за
десять лет.

### Источники и тип данных

Источники — информационные системы филиалов. Их CSV-файлы содержат
структурированные табличные записи: читателя, книгу, филиал, дату и тип
операции. Это не свободный текст и не изображения, а регулярно загружаемые
пакетные данные.

### Пакетная или потоковая обработка

При ночной передаче подходит пакетная обработка: за один запуск принимается и
обрабатывается накопившийся файл. Потоковая обработка нужна, если выдачи и
возвраты должны появляться в системе почти сразу после операции.

### Оценка объёма

```text
40 МБ в сутки × 365 дней × 10 лет ≈ 146 000 МБ ≈ 146 ГБ
```

Это оценка исходных данных. Резервные копии, промежуточные слои, индексы и
служебные данные увеличат фактическое место.

### Нужны ли предложенные компоненты

**Брокер событий.** Для готовых ночных CSV он не обязателен: данные приходят
пакетами. Брокер нужен при переходе к передаче каждой выдачи и каждого возврата
как отдельного события.

**Распределённый движок.** При 40 МБ в сутки он не обязателен. Обычной
пакетной обработки достаточно. Spark или аналогичный движок оправдан при
значительном росте данных, сложных преобразованиях или необходимости
распределённого расчёта.

**Колоночная СУБД.** Она полезна для месячных отчётов по большой истории:
аналитический запрос читает много строк, но обычно ограниченное число колонок.

### Запрос библиотекаря

Запрос «что сейчас находится у читателя» — оперативный, то есть OLTP-поиск.
Его лучше обслуживать из реляционной операционной базы, например PostgreSQL,
где хранятся актуальные состояния выдач. Аналитическое хранилище предназначено
для отчётов и не должно быть единственным источником оперативного ответа.

### Риски ночных выгрузок

- файл может опоздать или не прийти;
- файл может быть неполным;
- один файл могут передать повторно;
- в данных могут появиться дубли;
- структура CSV может измениться;
- возможны неправильные даты и пропущенные возвраты;
- исправления задним числом попадут в систему только после следующей загрузки;
- до ночной загрузки отчёты не видят новые операции.

### Один из вариантов архитектуры

```text
филиалы
    ↓ ночные CSV
объектное хранилище / RAW-слой
    ↓ пакетная обработка и проверки
PostgreSQL с актуальными выдачами
    ↓ историческая загрузка
Parquet или колоночное аналитическое хранилище
```

Здесь операционная база отвечает на быстрые запросы библиотекаря, а
аналитический слой — на отчёты за месяц и анализ истории. RAW-слой сохраняет
исходные файлы, чтобы ошибочную обработку можно было пересчитать.

## Вопросы преподавателя и короткие ответы

### 1. Что такое grain таблицы `orders_enriched`?

Grain — одна строка на один заказ. Это означает, что `order_id` должен быть
уникальным, а все показатели относятся ко всему заказу.

### 2. Почему нельзя соединить `raw_orders`, `raw_items` и `raw_payments` напрямую?

Потому что и позиции, и платежи связаны с заказом как 1:N. При одновременном
соединении возникают все сочетания позиций и платежей внутри заказа, поэтому
строки и суммы размножаются.

### 3. Сколько CTE нужно в задании 1 и почему?

Нужно два CTE: один для платежей и один для позиций. Каждая таблица отдельно
сворачивается по `order_id`, после чего обе свёртки безопасно соединяются с
заказами.

### 4. Почему используется `LEFT JOIN`?

Чтобы сохранить заказ даже при отсутствии платежей или товарных позиций.
Пропущенные показатели затем заменяются нулями через `COALESCE`.

### 5. Почему `payment_count` — это не количество заказов?

Это количество строк платежей для конкретного заказа. Один заказ может иметь
несколько платёжных операций.

### 6. Почему `order_date` приводится к `DATE`?

Исходное поле содержит дату и время, а для анализа нужны календарные даты и
месяцы. Тип `DATE` убирает время и делает группировку однозначной.

### 7. Почему задание 2 строится из `orders_enriched`?

Потому что там уже одна строка на заказ и рассчитан `items_total`. Если считать
выручку непосредственно по неагрегированной таблице после нескольких JOIN,
можно получить задвоенные суммы.

### 8. Почему в `monthly_revenue` используется `COUNT(*)`?

Потому что в `orders_enriched` одна строка соответствует одному заказу.
Поэтому количество строк в месяце равно количеству заказов в месяце.

### 9. Чем `GROUP BY` отличается от оконной функции?

`GROUP BY` схлопывает строки в группы. Оконная функция оставляет строки и
добавляет к каждой результат расчёта по окну. Накопительный итог нельзя
получить простым `GROUP BY` без потери отдельных месяцев.

### 10. Что делает `LAG`?

Возвращает значение из предыдущей строки в заданном порядке. Здесь он берёт
выручку предыдущего месяца.

### 11. Почему для первого месяца `revenue_prev` равен `NULL`?

У первого месяца нет предыдущей строки. Это отсутствие предыдущего значения, а
не нулевая выручка.

### 12. Что означает `ROWS UNBOUNDED PRECEDING`?

Окно начинается с первой строки и заканчивается текущей строкой. Поэтому
`SUM(revenue)` считает накопительный итог от начала истории.

### 13. Как проверить, что суммы не задвоились?

Сравнить сумму `payment_total` с суммой `payment_value` в `raw_payments`, а
сумму `items_total` — с суммой `price` в `raw_items`. Они должны совпадать с
небольшой допустимой погрешностью чисел с плавающей точкой.

### 14. Зачем нужен `CREATE OR REPLACE TABLE`?

Чтобы повторный расчёт пересоздавал результат и не дописывал к нему дубли.
Это пример идемпотентного поведения.

### 15. Почему Parquet удобен для аналитики?

Он хранит данные по колонкам, поэтому аналитический движок может читать только
нужные поля. Кроме того, однотипные значения колонок хорошо сжимаются, а схема
хранится вместе с данными.

### 16. В чём разница между OLTP и OLAP?

OLTP обслуживает небольшие оперативные запросы и изменения отдельных записей.
OLAP выполняет тяжёлые аналитические запросы по большим объёмам данных. Поиск
текущих книг у конкретного читателя — OLTP, месячный отчёт по всей истории —
OLAP.

## Что сказать о главном результате ЛР2

В лабораторной создано аналитическое представление данных без размножения
строк. Сначала платежи и позиции приведены к grain заказа, затем соединены с
заказами через `LEFT JOIN`. На этой безопасной таблице рассчитана месячная
выручка, накопительный итог и значение предыдущего месяца оконными функциями.
Результат хранится в DuckDB и дополнительно выгружается в Parquet.
